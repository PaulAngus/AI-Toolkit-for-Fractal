# Back up, edit and verify saved presets

General task: make a narrowly specified persistent change while proving both the intended result and preservation of unrelated data.

Before editing, capture the exact model/firmware, target address, saved image and integrity results. Bind the plan to a content hash. Keep the live edit buffer distinct; loading another preset may discard unsaved changes even if the saved backup is correct.

A received dump is a verified **read** artifact only after its assembly/checksums pass. It is not automatically a valid device **restore** stream. Establish the target-specific restore transaction, destination addressing and saved readback separately before relying on automatic rollback.

Songs/setlists belong to System data and persist without preset Save. The [System format investigation](../../docs/setlists-system-format-research.md) retains partial editor-file evidence and the unresolved complete-backup/recovery requirements. A preset capture does not back up these records. Keep complete System bytes and exact model/firmware/application provenance private; the single-preset `check-backup` and upload operations do not accept System files.

Use a disposable pilot for a new write path. Check intended live fields, preserve names, routing, other parameters/messages and the saved default scene, then save to the exact slot. Read stored data back and check persistence independently of the editor's live buffer. Silence after a command or absence of a rejection is not a positive acknowledgement.

Compare decoded meaning and preserved sections. Normalized comparisons may exclude documented representation differences such as CRC or compression encoding; they must not silently hide meaningful opaque fields. Record every excluded field and its validation basis. A fixed insertion length or a matching byte pattern does not prove preservation.

On a timeout or interrupted connection, reread and reconcile before deciding whether another write is needed. A resume record needs the original hash, verified resulting hash, target, operation parameters and persistence outcome. A saved plan file or backup's existence is not proof that hardware changed successfully.

Report partial batches honestly. If preservation fails, stop further writes and diagnose the difference. Restore only through a separately verified operation. Receiving equipment's reaction is another outcome: correct saved PC settings do not establish downstream behavior.

The [read-only runtime](../../docs/runtime.md) captures integrity-checked saved data with exact bytes/hash manifests. Planning is common across the three target models. The [0.4.0 editing pilot](../../docs/editing-pilot.md) physically qualified FM9 12.00 PC/CC editing and operation-based recovery of an empty preset, with exact original saved body/raw comparison. Its shared preservation checker validates the actual inserted instance interval; shape-record offsets include part of the following prefix. That pilot did not qualify full-dump upload/restore. Later FM9 12.00 general-edit trials physically qualified persistence and exact undo of one mapped Amp Drive saved word, a compound Amp Bass/Mid edit and one existing modifier-source edit. These establish exact saved-byte changes, not audible scale calibration or effective modifier response. See [editing validation](../../docs/preset-editing-validation.json). Existing-block Scene MIDI execution has a separate 0.7.0 operation. Full-preset restore and isolated insertion have separate subsequent evidence. A partial pilot can be reconciled only against retained/current hashes and ownership checks.

When a replacement compressed stream is shorter, clear only the bytes vacated within the previous stream interval; preserve opaque padding beyond it. Compare the complete decoded body and opaque bytes after upload before Save. A stopped FM9 modifier trial exposed this boundary: the device zeroed a vacated byte, the verifier refused Save, and query-only reconciliation plus guarded Reload restored the original buffer. A corrected fresh trial passed Save/Reload and exact undo.

The [full-preset qualification record](../../docs/restore-qualification.md) includes actual file integrity inspection, saved/loaded-state comparison and separately qualified toolkit restoration. Release 0.4.1's [offline `check-backup` command](../../docs/runtime.md) accepts a single model-sized preset transfer with an opaque header, without assigning a destination. Saved snapshots still require valid addressed headers. Reject bank/system/cab/firmware transfers, extra frames, wrong models and corruption.

Equal live channels do not establish equality of saved data. Treat decoded-word differences as content differences, never exclude them merely because a restore sounds correct or raw compression changed. Distinguish file integrity, loaded-buffer status and complete saved readback.

For a controlled recovery test, capture the deliberately changed saved state before restoring. Compare its complete body with the original: establish the exact intended differences, retain all other bytes and verify stable repeated reads. Correlate current block status, saved fields and numeric instance identities; a caller's label or a record's shape can identify the wrong block.

When the original is already loaded, use the distinct [save-current operation](../../docs/save-current.md) to persist it: bind the expected backup and saved base to hashes, check the selected target/scene and live expectations, retain a fresh base, send one authorized Save, and compare the full saved raw image and body with the original on repeated reads. The expected file is never transmitted. FM9 12.00 passed exact equality with no excluded fields. This qualifies saving the loaded buffer; this save-only evidence does not qualify file upload or other-model hardware.

Confirm the complete manufacturer's save sequence, rather than treat entering a Store menu as persistence. For FM9, [Saving Changes, printed p47](https://www.fractalaudio.com/downloads/manuals/FM9/FM9-Owners-Manual.pdf#page=53) requires STORE, the intended destination, ENTER, ENTER and the “SAVED!” indication. Do not carry this exact UI sequence to other models without their documentation. Unchanged saved hashes establish the observed saved state, not why a save did or did not occur. Preserve the live restored buffer and reconcile the actual actions/destination before a reload or another mutation.

Release 0.5.0 implements the [generic full-preset restore sequence](../../docs/preset-restore.md) separately: strictly inspect and hash the source, compare fresh saved and live baselines, upload once to temporary memory, verify complete bytes before Save, repeat the saved read and verify after Reload. The opt-in qualifier compares all other saved slots against before-test captures. Consult the [current qualification record](../../docs/preset-restore-validation.json) for measured model/firmware scope. No automatic rollback, cross-model conversion or batch guarantee follows from this operation.

Release 0.6.0 adds [isolated insertion](../../docs/block-insertion-execution.md) with an actual-record projection that preserves every existing body byte and raw header/padding. FM9 12.00 passed 52 saved/reloaded insertions, 51 existing MIDI tables preserved and all 460 non-target saved slots unchanged. Two pre-edit identity timeouts stopped their requests; freshly unchanged remaining baselines preceded deliberate new requests. Consult [the qualified record](../../docs/block-insertion-validation.json). No write is automatically retried or rolled back, and other-model physical evidence remains missing.

Release 0.7.0 supports [existing-block Scene MIDI execution and explicit undo](../../docs/scene-midi-execution.md). An undo receipt comes only from complete saved/reload verification and binds the original upload to the exact result hash. Fresh saved/live comparison prevents discarding later work; the result hash and complete original loaded buffer are rechecked immediately before the undo Save. This restores a whole backup rather than merging later changes. Consult [actual PC/CC/model qualification](../../docs/scene-midi-execution-validation.json); uncertain partial-edit recovery, block removal, automatic rollback and persistent resume remain separate.

## Persistent Scene MIDI receipts and batch undo

[Release 0.8.0](../../docs/scene-midi-recovery.md) adds private hash-bound original/result records, exclusive ownership and flushed pre-attempt checkpoints. Import rebuilds each original plan and verifies complete saved/reloaded result equality before a receipt is available. Fresh saved/live checks remain required. Deliberate resume distinguishes exact originals, complete intended results and conflicts; an uncertain Save with a verified complete result is not resent. Explicit batch undo stops on later changes and retains each completed original. An unsaved partial upload/edit is never discarded or automatically saved. See [qualification](../../docs/scene-midi-recovery-validation.json) before extrapolating software interruption tests to hardware.

[Selective Scene MIDI undo](../../docs/selective-scene-midi-undo.md) applies to completed saved **general-edit** receipts containing only existing Scene MIDI message edits and to completed persistent Scene MIDI recovery-store items. It compares original/result raw row words with a caller-supplied current saved capture, restores exact receipt-owned words from a hash-bound original and preserves later unrelated settings. Conflicting owned rows stop planning. The resulting complete-image bundle needs a fresh standard review and saved/live preflight; unfinished recovery records do not qualify and hardware remains untested.
