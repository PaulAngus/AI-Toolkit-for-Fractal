# Tempo, tuner and looper controls

Release 0.36.0 adds shared capture-bound performance controls for FM9, FM3 and Axe-Fx III at both capacities. [PerformanceControl.cs](../src/Fractal.Core/PerformanceControl.cs) implements closed requests and verification; CLI/MCP delegate to it. [Validation](performance-controls-validation.json) is synthetic only. Implementation does not authorize hardware access.

| Kind | Fields | Execution and evidence |
| --- | --- | --- |
| `tempo-read` | None | One explicitly reviewed tempo query. Retains BPM and compares complete preset context. |
| `tempo-set` | Integer `bpm`, 20–250 | Reviewed query before set; same BPM is a no-op. One set otherwise, then one query and complete context comparison. |
| `tempo-tap` | None | Exactly one tap event. No interval inference, repeated taps or tempo query. `state_verified: false`. |
| `tuner-set` | Boolean `enabled` | Explicit on/off command. No documented state query or verified no-op; `state_verified: false`. |
| `looper-button` | `action`: record, play, undo, once, reverse or half-speed | Exactly one button event. Flags observed before/after; they cannot verify audio contents, undo or every event effect. `state_verified: false`. |
| `looper-state` | `action`: play, reverse or half-speed; Boolean `enabled` | Fresh flags must match retained context. Desired flag already set is a no-op; otherwise one button and readback. All other flags must remain equal. |

Each request is schema 1 with an exact `PerformanceControlContext`: a complete `LiveControlContext` under `preset`, plus a `looper` observation when a model-qualified Looper is present. Unrelated request fields and missing/invalid values are refused. Looper controls require a present block; the six-button protocol supplies no instance address. No arbitrary SysEx or parameter numbers are accepted.

The manufacturer [MIDI specification](https://www.fractalaudio.com/downloads/misc/Axe-Fx%20III%20MIDI%20for%203rd%20Party%20Devices.pdf) documents Axe-Fx III forms: 0F button/query and six-bit state, 10 tap, 11 tuner Boolean and 14 little-endian septet-pair BPM/query. Its specification scope is firmware 1.13+. FM9 and FM3 use their own model byte. The pinned Gen-3 codec independently binds tempo queries to each model; the pinned FM9 protocol also implements tempo read/set. Remaining FM9/FM3 command adaptations are explicit inference from the documented Gen-3 forms. None is toolkit hardware qualification. Command framing is separate from block identity, exact firmware behavior and verification.

Each model's own owner manual documents whole-number 20–250 BPM: [FM9](https://www.fractalaudio.com/downloads/manuals/FM9/FM9-Owners-Manual.pdf), [FM3](https://www.fractalaudio.com/downloads/manuals/FM3/FM3-Owners-Manual.pdf), [Axe-Fx III](https://www.fractalaudio.com/downloads/manuals/axe-fx-3/Axe-Fx-III-Owners-Manual.pdf). Changing tempo can update both global tempo and the current unsaved preset tempo. **No Save is sent.** A later caller-issued Save could store that preset tempo; global tempo is outside the preset backup. Tempo-to-use, controller channel settings, external clock and tap averaging are not modified or inferred.

The [pinned upstream SysEx map](https://github.com/TheAndrewStaker/mcp-midi-control/blob/59047175cfc4f23e092931b54a7c54f2bffde3ea/packages/fractal-midi/docs/devices/axe-fx-iii/SYSEX-MAP.md) reports that the tempo query acted as a set on unspecified early Axe-Fx III firmware. This is an upstream report, not a retained toolkit hardware observation; it supplies no exact firmware gate. Consequently 14/7F7F is **outside the general read allowlist**, ordinary snapshots never issue it, and even `tempo-read` needs exact trusted-host review and enabled writes. If the query changes captured preset state, execution stops before any set. A global-only side effect cannot be excluded by preset captures.

Persistent preset state, loaded bytes, selection and effective block status must remain exactly equal to the reviewed context. Current tempo words have no qualified saved-body mapping. A native tempo change that modifies loaded bytes therefore produces `stopped-uncertain`, with observed BPM and full before/after captures retained. It is not treated as verified preservation or silently exempted. Reconcile those private captures and do not replay a command to obtain confirmation. This limitation is an explicit boundary of this release, not a reason to map every block parameter.

The session serializes requests, checks exact model/function/length/checksum and value bounds, excludes checksumless pushes from reply correlation and observes relevant rejection replies. A scope can be claimed once. Sends and queries have finite budgets; timeouts, cancellation and uncertain replies stop without retry, automatic undo, reload or Save. Tempo replies carry no transaction address, so an indistinguishable same-model unsolicited reply remains a correlation limit. Tuner pitch or tempo pushes do not verify requested state; the manufacturer's push description covers MIDI Out, not USB.

CLI discovery: `fractal performance-capabilities --model MODEL --capacity N --firmware VERSION`. Capture: `fractal capture-performance --model MODEL --capacity N --firmware VERSION --input N --output N --destination NEW_PRIVATE_DIRECTORY`; it captures saved/loaded images and queries looper flags only when present, never tempo. `--validate-only true` checks capture arguments offline. The normal transport ownership rules apply to local and explicitly configured network connections.

The opt-in helper uses `--hardware --performance-control --request REQUEST_JSON --expected-hash SHA256 --validate-only true` for offline request validation. Actual execution additionally needs the authorized connection and new evidence destination. It verifies identified model/capacity/firmware before execution. This helper has no unscoped execution path.

MCP exposes `fractal_query_performance_capabilities`, `fractal_capture_performance_context` and `fractal_prepare_performance_control`. Preparation freezes the private capture and exact request with normal device/version/input binding. Execution uses existing exact trusted-host approval, one coordinated owner and consumed reviews. Events and tuner commands terminate as `sent-unverified`; `completion_verified` remains false while the result is readable. Absolute queried-state success terminates as `verified-complete`. Evidence remains private and never becomes a saved-edit/undo receipt.
