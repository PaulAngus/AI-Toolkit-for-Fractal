# Preset organization

Release 0.37.0 implements saved preset organization for FM9, FM3 and Axe-Fx III at both capacities. [PresetOrganizationPlan](../src/Fractal.Core/PresetOrganization.cs) compiles immutable captures into existing [complete-image edit plans](preset-editing.md) and [ordered batches](batch-editing.md). [Validation](preset-organization-validation.json) is synthetic only. No implementation or offline review authorizes hardware access.

| Operation | Required intent | Result |
| --- | --- | --- |
| `rename` | `slot`, `name` | Change only the 32-byte raw name field and required integrity values. Body, scene names, settings, routing, MIDI and default scene stay unchanged. |
| `copy` | `source_slot`, `destination_slot`; `overwrite: true` if changed | Copy the complete original source image to the destination. Optional `name` applies an explicit destination rename. |
| `import` | `destination_slot`, complete donor with declared model/capacity/firmware and SHA-256; overwrite if changed | Stage one integrity-checked same-context Gen-3 preset file. No conversion or bank-file parsing. |
| `move` | Distinct source/destination, overwrite if changed, `vacated_policy: replace-from-capture`, explicit other `replacement_slot` | Write the original source to the destination, then the chosen original replacement image to the vacated source. No fabricated empty preset. |
| `swap` | Distinct source/destination slots | Exchange both original images, including their names and saved default scenes. |
| `reorder` | Distinct `assignments` forming a closed source/destination permutation | Derive every destination from its original donor, with writes in the supplied order. Cycles never consume intermediate writes. |

Slots are zero-based and validated against explicit capacity. A request contains schema 1, model/capacity/firmware, 1–64 distinct `SavedPresetGuard` captures (`slot`, `sha256`, base64 `capture`) and 1–32 operations. Supply exactly the referenced saved slots. At most 32 distinct destinations are allowed. Duplicate destinations and unrelated operation fields are rejected; use the copy/import `name` field to combine a rename. Names have a toolkit limit of 0–31 printable ASCII characters without trailing spaces. A decoded name already equal to the intent preserves its original raw representation.

All assignments use immutable **original** captures. Overlapping copies therefore have snapshot semantics: a source that is also overwritten remains the original donor for another assignment. Changed copy/move/import destinations always require explicit overwrite, even when a preset appears empty. Swaps and permutations explicitly identify the displaced images through their mappings. Originals and donor hashes remain in private immutable requests. The preview includes source/destination roles, names, original/result hashes and before/after default scenes; the plan hash also binds the canonical complete request.

Copy, import and relocation retain the donor's complete decoded body, scene names, Scene MIDI, settings, routing, opaque raw header and padding. Only reviewed address retargeting, optional name changes and narrowly qualified compression equivalence are allowed. Rename preserves the existing default scene; whole-image assignment preserves the donor default scene. The pinned [Gen-3 source](https://raw.githubusercontent.com/TheAndrewStaker/mcp-midi-control/59047175cfc4f23e092931b54a7c54f2bffde3ea/packages/fractal-gen3/src/presetBody.ts) lines 692–697 corroborates the uncompressed name field at 0x08 for 32 bytes, independently of the toolkit decoder. Model-specific addressing, dump sizes, integrity rules and contained profiles remain separate. Source hashes and synthetic checks do not establish physical compatibility.

The manufacturer [preset management guidance](https://support.fractalaudio.com/en-US/installing-factory-presets-1410465) describes previewed copying, relocation and individual import/export for these devices. That guidance establishes useful operations, not this toolkit's wire implementation. Imports require matching declared context; byte integrity cannot establish firmware origin, asset availability or hardware identity.

Preparation binds a retained `LiveControlContext`, every destination original and all captured sources. The existing executor loads the original destination/default scene when necessary, verifies its saved/loaded base, uploads temporary memory once, verifies the complete result, saves once, verifies repeated saved equality, reloads and verifies again. Source/destination guards are read before the first mutation, around each target transition/upload and at final verification. Completed destinations are compared against their observed verified hashes, while untouched sources/destinations must still match originals. No-op batches send queries only and verify unchanged complete current context at the end.

A copied default scene can differ from the destination's original scene. The upload scope now binds separate before/result scenes. Before Save, alignment is permitted only after the exact saved baseline and full uploaded content are verified, allowing solely the known selected-scene word variant. After Reload, a separate guarded alignment can handle a device-selected scene. Each phase can send at most one scene command; unrelated loaded changes or ignored commands stop before further mutation. Recall/scene alignment may emit configured Scene MIDI and invoke scene-revert behavior, so complete-image readback remains mandatory. Hardware behavior for this organization sequence is unqualified.

Organization is **not atomic**. Each destination is its own verified transaction. Durable progress binds the batch hash, current release, completed prefix, active index, phase and failure. Timeout, cancellation, rejection, stale source/destination or unrelated changes stop without automatic upload/Save replay or rollback. Results distinguish verified completed targets from an uncertain active target and untouched pending targets. Query-only reconciliation compares all planned originals/results and source guards without loading or changing anything. Sampled endpoints cannot exclude transient changes between reads.

Receipt-based undo accepts current-release completed or stopped organization progress, exact progress hash, immutable batch and completed-item receipts. It revalidates each fully completed changed target and its saved/reloaded images; uncertain and untouched targets are ineligible. Current saved captures must equal the recorded observed result or exact original. Later changes are refused. The inverse plan restores originals in reverse completed order through a fresh ordinary organization review. Already-original targets become no-ops. Unsaved current work still needs preservation or an explicit captured discard choice. Undo is also non-atomic; there is no automatic resume/recovery engine for an uncertain upload or Save.

Songs, footswitch assignments, MIDI mappings, user-cab identities/slots and system settings are not rewritten or backed up by these operations. A relocated preset can leave external references pointing to the old slot. Imported presets can depend on caller-managed assets or global configuration. Those changes require their own supported operations and evidence.

CLI offline commands:

```text
fractal plan-organization --request REQUEST_JSON --destination NEW_DIRECTORY
fractal inspect-organization --bundle DIRECTORY --expected-hash SHA256
fractal organization-batch --bundle DIRECTORY --expected-hash SHA256 --context CONTEXT_JSON --discard-changes true|false --destination NEW_DIRECTORY
fractal plan-organization-undo --receipt EXECUTION_DIRECTORY --expected-hash PROGRESS_SHA256 --request CURRENT_CAPTURES_JSON --destination NEW_DIRECTORY
```

The compiled bundle uses the existing opt-in `--hardware --edit-batch --bundle DIRECTORY --expected-hash SHA256 --mode apply|reconcile --validate-only true` helper for offline validation. Actual execution requires explicitly authorized connection/destination and the exact trusted-host review. The ordinary planner opens no MIDI ports and supplies no port, preset or blank-image defaults.

MCP tools: `fractal_plan_preset_organization`, `fractal_inspect_preset_organization`, `fractal_prepare_preset_organization`, `fractal_prepare_organization_reconciliation` and `fractal_plan_preset_organization_undo`. Planning selects referenced captures from an integrity-checked backup artifact. Import additionally takes confined donor artifact/file/hash and explicit model/capacity/firmware labels. Preparation freezes organization plus existing live-control context into a guarded batch; normal exact approval, consumed reviews and one coordinated owner apply. `fractal_inspect_attempt` exposes a retained batch progress hash when available. No arbitrary shell, SysEx or unmapped parameter interface is added.
